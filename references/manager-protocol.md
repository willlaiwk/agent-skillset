# Manager protocol

## Planning

Read project instructions before `init`. Save/display the returned manager ID; resume by explicit ID. Initialization creates ignored namespaced state without committing or modifying the user's `.gitignore`; it does not claim/reconcile. Claim an initially released manager with a private owner credential outside worker artifacts, then supply selector/credential on management commands. Retain and reuse a valid credential across compaction. For a planned handoff use `owner release`; to replace an active owner, use `owner takeover --expect-generation N --reason ... --session-id ... --credential-file ...` with a fresh private file. Do not manually overwrite owner state. Both operations fence the old credential while preserving workers and files; no timeout or PID automatically transfers control. Read-only status/peek/inbox/events are available without control.

As the valid owner, write `.manager/{ID}/plan.md` with the requested outcome, scope, acceptance criteria, task dependencies, delivery branch/tree, known user changes, decisions, integration progress, and final verification evidence. Task IDs such as `T001` are local to each manager. Worker limits also apply per manager, not repository-wide. Legacy v1 state blocks normal v2 commands; follow [explicit migration](runtime.md#explicit-v1-migration) with a zero-write preview, source hash and quiescence assertion. Migration never stops writers or restores old provider conversations. Claim its released owner explicitly; historical acceptance needs new review/verify/accept. Interrupted migration requires the recorded ID for forward resume; preserve both sides on external changes.

Create task briefs using the template. Dependencies must reference previously registered tasks, which keeps the MVP graph acyclic. `task` registers queued work; `spawn` starts work only after dependencies are manager-accepted. The manager schedules runnable tasks itself; there is no background scheduler.

Every worker gets a private worktree. Registration resolves `--base` (default current committed `HEAD`) to a fixed commit, not uncommitted changes. A dependent worker does not automatically receive a dependency's branch: prepare a committed integration ref before registering it and pass that ref as its base. Existing queued definitions keep their base, including after migration; use a fresh task ID when replanning requires a different base. Record that choice and the retained task's disposition in the plan. See the [migration-to-delivery example](runtime.md#continue-from-migrated-acceptance-to-dependent-work).

## Supervision loop

1. Run namespaced `status` and read its persisted tasks plus live `observed` diagnostics; use owner-only `reconcile` to persist report changes. Status/peek do not write state. Only manager state `done` with current acceptance eligibility counts as accepted.
2. For `needs_manager`, inspect the question and repository evidence, then `send` an answer. If user judgment is essential, record `escalate`, ask the user, and send their answer when available.
3. Inspect the pane only for diagnostics, including native permission/trust/login prompts. Do not auto-confirm a prompt. A persisted inbox survives failed delivery; `send --inbox-only` avoids pasting into a busy UI. Only send to the terminal when the worker is ready; `inbox` lets you inspect unacknowledged messages.
4. For `verification`, read `result.md`, inspect the diff from the recorded base, and compare work to each acceptance criterion. Inspect commands before running project-configured checks. Save an independent review and run `verify --review ... --command ...`.
5. On failure, `send` a focused correction to the existing session. This invalidates verification. If dead, diagnose, `retry`, and use retained result/worktree/history as context. Two restarts after the initial attempt are the default limit.
6. `accept` requires a successful verification record bound to current worktree contents, report, attempt/assignment identity, and review. It stops the matching worker and records task acceptance. Use `integration init --base REF` to create this manager's isolated branch/worktree. Integrate there using ordinary repository tools under existing authorization, preserve accepted task trees, resolve conflicts within scope, and commit a clean combined candidate. Run `integration verify --target refs/heads/TARGET --source TASK --review FILE --command CMD`, repeating sources as needed, and inspect `integration status` to recheck the evidence. Sources must be current accepted snapshots; your review establishes that the candidate includes them. The runtime never imports/stages sources automatically. Keep concurrent managers out of the shared user checkout.
7. Under existing delivery authorization, `deliver --verification RUN_ID` fast-forwards only the recorded existing local branch if no registered worktree has it checked out. The short common gate rechecks owner/evidence/inventory and uses an expected-OID transaction plus unique receipt. A stale target needs deliberate integration and a new verification; a checked-out target uses the repository's existing authorized external delivery workflow. Reconcile interrupted delivery before retrying: matching receipt proves completion, missing receipt with unchanged old target permits fully rechecked retry, and ambiguous/external-change states require diagnosis. Preserve journals and receipt refs; no automatic cleanup or force/push/PR is provided.

The runtime enforces a structural verification gate, not semantic correctness: you remain responsible for the adequacy of review and commands. For a research-only task, independently check cited evidence and use an appropriate artifact validation command rather than inventing irrelevant code tests.

## Recovery

Use `owner status` to inspect credential validity, owner journals and pending task operations without writing. A fenced session stops management commands and direct plan/integration edits. The new owner respects operation busy: manage other tasks or inspect while a previous check runs; do not delete locks or assume takeover stops check children. Long verify submits only after owner/assignment/snapshot checks, and returns `fenced` or `snapshot_changed` without current verification eligibility when those checks fail. A successful completed verification can survive takeover, subject to the usual acceptance recheck.

An owner-only `reconcile` repairs committed owner events once, diagnoses uncommitted credentials without activating them, and classifies interrupted verification only after obtaining its operation lock and checking its journal/snapshot. It never infers check success. Verify children may survive abrupt runtime death; legally quiesce them before further task edits. Pending short-operation intents need inspection rather than an assumed successful send/stop/accept. Integration uses its own operation lock outside the Git tree; its long checks similarly permit other tasks/managers/reports and fence after handoff. Interrupted integration init can resume only when the retained ref/registration/tree match its recorded base; ambiguous or changed artifacts are preserved for diagnosis. Combined proof journals do not restore success after interruption; record eligibility requires an owner-committed hash index and current candidate/target/source/review checks.

`reconcile` reads only the selected manager's reports, inventories matching tmux windows and registered worktrees, flags stale reports (default 15 minutes), and marks missing/crashed workers or worktrees as failures. Full tmux root/manager metadata must match; unmarked or foreign sessions are rejected. Other managers' resources are not adopted as orphans. Stale means inspect, not automatically kill. Orphans are reported, never killed/deleted. Corrupt reports are explicit errors, never success.

An interrupted launch is recovered from namespaced session/window identity. Reconcile can rediscover its pane. `retry` preserves branch/worktree/history, increments the attempt and replaces the assignment ID; old report/inbox/ack identity is rejected. Old message acknowledgment remains historical, not current-attempt receipt. A retry begins a fresh interactive conversation with the original brief, prior result, and correction context; it does not promise provider conversation resumption after a process dies.

Do not remove state, branches, logs, or worktrees during recovery. If state is corrupt or a project moved, stop and repair from preserved artifacts with appropriate authorization; do not initialize over it. The runtime does not recreate missing state automatically or claim to restore unrecorded user intent.
